## 検証（重要）

**移植したものが実際の経路から使われることを示すこと。** 新しい型・関数・状態機械を
足しただけで、既存の描画・入力・保存の経路がそれを通らないなら、**移植は成立していません**。
ユニットテストは新しいコードを直接叩くので通りますが、画面は何も変わらないか、壊れます。

報告に**呼び出し箇所を file:line で挙げること**。「定義した」ではなく
「どこから呼ばれるか」を示してください。既存の実装を置き換えたなら、
**置き換えられた側が消えていること**を grep の件数で示すこと。
両方が残っているのは、移植ではなく二重実装です。

実際にこれで差し戻した例:
- `syncCommandPaletteActions` を定義したが呼び出しが 0 件。ObjC の固定配列が使われ続けた
- `WindowInvalidator` と `DrawPhase` を入れ、29/29 全テスト成功。**サイドバーが描画されなくなった**

**受け入れ条件のテストを必ず残すこと。** 受け入れ条件に「assert する」「一致する」
「〜になる」と書かれた項目は、**その場で確かめただけでは満たしたことになりません。**
`tests/test_*.nim` に残り、`tests/test_runner.nim` が拾って実行されるところまでが
条件です。既存ファイルに足すなら、そのファイルのテスト数が増えることを確認すること。
「意図しないテスト差分」として消さないこと。

**`nimble test` の終了コードを信用しないこと。** この環境の nimble は常に 0 を返します。

```
nim c --mm:arc --nimcache:.nimcache/test_runner -r --path:src tests/test_runner.nim
```

`実行: 27 / 成功: 27 / 失敗: 0` と rc=0 を確認すること。
**件数が 27 未満なら、通ったのではなく走っていません。**

**衝突マーカーやビルド失敗が残っていても、キャッシュされたバイナリで
テストが通ることがあります。** 疑わしいときは `.nimcache/test_runner` を消してから
走らせてください。

`test_executor.nim` と `test_extension_service.nim` は稀に落ちます（既知の不安定）。
落ちたら 1 度だけ再実行し、それでも落ちるなら報告してください。

`nimble format` と `nimble lint` も実行してください（rc ではなく出力を見る）。

### 本体のビルドも必ず確認すること

```
nim check --mm:arc --nimcache:.nimcache/chk --path:src src/nimculus/main.nim
```

**ランナーは `main.nim` をコンパイルしません。** 型を変えると
テストが 27/27 のまま本体が壊れます（2026-08-12 に実際に起きました）。
`Error:` が出ないことを確認してください。所有外だから直せない場合は、
実施せず報告して止めること。

## 制約

- `nimble clean` を実行しない、`tools/ink_check.py` と `tools/scroll_shift.py` を消さない
- **`tools/ui_test.sh` を実行しない**（VM は排他資源。依頼側が直列に回す）
- `open -n` で起動しない、無関係な整形を混ぜない、依存を追加しない
- **コミットしない**（差分を残して報告する）
- 条件を通すための識別子の改名をしない
- 設計文書（`DESIGN_DECISIONS.md`, `docs/` 以下）を書き換えないこと
- テストを通すためにテストの形を変えないこと
- **`references/zed` に触れないこと**（シンボリックリンク。実体は本体側）
- `references/` 以下のサブモジュールを更新しないこと

**上記以外を変更しないこと。** 受け入れ条件が所有外を要求する場合、
**必要なファイルを全部列挙して**報告し、止めてください。

**変更を巻き戻さないこと。** テストが落ちても、原因を報告して差分は残してください。
あなたの sandbox では外部サービスに届かず落ちるテストがありますが、
依頼側の環境では通ります。それを理由に実装を捨てないでください。

**既に実装済みなら、受け入れ条件を 1 つずつ確認した結果を示して報告してください。**
「実装済み」だけでは判定できません。
